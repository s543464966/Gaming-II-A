## 文档维护与交付

- **策划方案**：只维护 `../product_plan.md`，将用户已确认的产品构想和玩法调整更新到正文，不另存策划版本。
- **产品需求文档**：仅在用户明确要求制作或更新时，根据当次需求、最新策划方案和本次交付范围编制新版本。保留已有版本，不覆盖、不删除、不将旧版同步改成新规则。沿用“范围名称-V版本号.md”命名，同一范围依次递增版本号；用户明确指定时遵从用户。
- **草稿与正式版本**：尚未编号、尚未交付的工作草稿可以持续完善；仅在用户明确要求形成交付或需求版本时，再保存为带版本号的正式文档。已经编号保留、已经交付或用户明确要求保留的文档不再覆盖。正式需求文档只表示本次需求已整理成版，不代表开发或验收已经完成。
- **新版内容**：写清版本、日期、所依据策划方案的更新日期及本次用户需求、本期做与不做的范围、交互规则和验收标准，并简要说明相对上一版新增、修改、取消的内容及其对设计、开发和验收的影响。本版实施所需规则直接写入正文，不能仅链接持续变化的策划方案。
- **版本使用**：本入口登记每一版需求文档，并区分最新文档与当前实施版本。策划方案的更新或新版草稿的产生，不自动替换正在实施的需求；根据用户明确的交付或调整指令更新实施依据。
- **实施中变更**：明确调整纳入本期还是后续、影响哪些设计和开发内容，再形成相应新版；设计、开发和验收共同使用明确采用的版本。用户已经明确范围与执行要求时直接承接，不重复要求确认。当前使用的图片与原型可能继续更新，历史需求以各版完整文字规则为准，不能通过更新共享附件默默改变旧版要求。
- **工作流程**：先分析用户提出的规则、说明合理性并优化表述；逻辑通顺后更新策划方案。用户明确要求制作产品需求文档时，再编制对应范围的新版本，核对规则及设计开发影响，并按明确采用的版本实施与验收。策划更新不自动生成需求版本。

当前局内实施依据为用户本次要求新增的 V1.3，V1.0、V1.1 和 V1.2 原样保留。历史文档中“持续更新本文件、不另存版本”等旧维护表述由本节规则替代。后续新增版本继续登记在上表。V1.3 是交付要求，不代表现有程序或100关配置已经完成或通过验收。

## 打开局内体验版

在项目目录执行 `node ./prototype_server.cjs.txt`，然后打开 [局内界面](http://127.0.0.1:4173/)。不需要安装额外依赖。服务只监听本机；关闭运行窗口或按 Ctrl+C 即停止。

现有原型采用4格需求池与旧版4×4盒位布局，可体验开局出餐、点击搬运、同味成组与容量拆分、等待需求、自动连续回收、原位补货、单次撤回和通关。画面由可调整的SVG与CSS绘制，参考图片没有被当作整屏背景。

当前关卡是用于体验界面的演示配置，不代表正式关卡、奖励或数值。解锁、置顶道具和后期特殊盒尚未实现，金币与钻石奖励尚未接入；页面入口会说明当前状态。本地浏览器原型不代表已完成微信小游戏接入或真机验收。

V1.3 已作为前100关局内设计与开发依据。现有原型仍使用旧4×4布局和演示关数据，尚需按V1.3补齐可配置三类摆位、固定盒位处理顺序、特殊盒开局状态及取放约束、完整关卡数据、首次归纳事件与周转难度验证；打开原型不能视为V1.3已通过验收。

运行基础逻辑检查：`node --test ../../Testing/planning/legacy_donut_sort_test.mjs`。
