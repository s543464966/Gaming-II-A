# 项目策划与设计资料

`Designing/` 统一保存项目的玩法策划、关卡设计、交互与 UI 说明、美术素材拆分、设计决策和验收记录。

文档使用有明确主题的 `snake_case` 文件名；内容较少时直接放在本目录，形成独立主题后再按需建立子目录。设计方案注明状态（草案、已确认或已替代），已替代的方案指向当前版本。

参考图继续保存在 `Archive/ReferenceImage/`，文档通过相对链接引用。游戏使用的素材与关卡配置保存在 `Coding/godot/`，设计文档记录意图与依据，不另存一套运行数据。

## 策划工作入口

产品策划同时承载产品设计总纲与完整玩法约束：说明做什么、为什么做，并明确合法操作、触发条件、对象、次数、顺序、限制、例外及系统关系。后续产品文档细化交互状态、配置、接口和交付标准，不能以“以后细化”为由从策划正文删除决定玩法结果的规则。专项明细可放配套资料；历史需求和后续已确认修订继续保留，来源冲突须明确标注。

2026-09-30 已将原“消除小游戏”策划工作区迁入本仓库。今后策划、数值、设计与开发均在这里维护；旧目录保留迁入前原件，不再作为编辑入口。迁入没有改写关卡或替换当前游戏美术。

当前实施依据是 V1.3、[R2 接入](r2_level_update.md) 和 [已确认局内调整](v1_3_alignment.md)，策划正文保留产品目标及影响结果的完整规则，实施继续结合上述文档。盒位按数量分排，每排尽量 4—5 个、最多 5 个，16—20 盒时使用四排；上下可见留白对称且每侧大于最大排间隙，不能用旧图的固定 4×4、围合或中间挖洞覆盖。采用左右补货、每关三种道具各一次、炸弹首次四同味归纳即解除，当前局内以同次操作连续回收计连单。原产品稿的跨操作八秒连单经济试算单独保留为待统一方案，不据此修改当前游戏。实际验收状态仍以实施记录为准。

策划方案更新已确认的产品设计，正式需求仅在用户要求形成或更新交付版本时新增，并在此登记；历史需求不随策划正文回改。开发完成与待验收内容记录在下方实施文档，静态稿、Excel 目标和旧原型都不能当作正式游戏的通过证明。

迁入检查记录：128 个来源文件整理为 100 个独立文件，261 处文件引用检查通过；工作簿、PNG 和 ZIP 的字节摘要与原件一致，旧原型的 4 项逻辑测试通过。原 `.codex-levels-build/` 中的一次性制作缓存及 `*.inspect.ndjson` 检查输出不迁入。上述数量与清单摘要描述迁入时状态，后续新增配套文档、编辑策划正文不回写该历史快照。迁入及本轮策划整理均未修改 Godot 源码或运行关卡，也未重新导出游戏。
